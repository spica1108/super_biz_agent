Behind the Code

Here's the actual code that handles your diagnosis request. On the left, the real source code from app/api/aiops.py. On the right, what it means in plain English.

CODE 

@router.post("/aiops")
async def diagnose_stream(request: AIOpsRequest):
    session_id = request.session_id or "default"

    async def event_generator():
        async for event in aiops_service.diagnose(session_id=session_id):
            # 发送事件
            yield {
                "event": "message",
                "data": json.dumps(event, ensure_ascii=False)
            }

            # 如果是完成或错误事件，结束流
            if event.get("type") in ["complete", "error"]:
                break

    return EventSourceResponse(event_generator())
PLAIN ENGLISH

📌 Line 1: Mark this function as a POST handler at /api/aiops — the doorbell for incoming diagnosis requests.

🔄 Lines 2-3: Define an async function that receives diagnosis requests and gives each conversation a unique ID.

📦 Line 5: Create an internal generator — a function that produces events one by one instead of all at once.

📤 Lines 6-11: Loop through each event from the AIOpsService and send it as a JSON message. The browser reads these live as they arrive.

⏹️ Lines 13-15: Check if the diagnosis is finished or hit an error. If so, close the stream.

📡 Line 17: Wrap the whole thing in an SSE response so the browser receives updates in real time.

The decorator @router.post is what tells FastAPI this function handles POST requests. The session ID keeps track of which conversation this diagnosis belongs to.

Three Key Patterns

The system is built on three architectural patterns. Together they make the diagnosis flow possible — from click to report.

🔄

Plan-Execute-Replan

The system doesn't guess an answer in one shot. It creates a plan, executes each step, then re-evaluates based on what it finds — just like a detective revising their theory.

📡

Streaming Output

Instead of making you wait minutes for a full answer, the system sends results as they happen. You see each step appear in real time via event stream technology.

🔧

Tool Integration

The LLM doesn't work from memory alone. It calls real tools — log checkers, metric queries, system commands — to gather actual evidence, just like a detective using forensic equipment.

The Plan-Execute-Replan Loop

Think, act, evaluate, repeat — the three-step dance that turns questions into answers

Playing Chess With Yourself

Imagine a chess player studying the board and planning three moves ahead. But unlike real chess, after each move you get to look at the new board and change your strategy.

That is the Plan-Execute-Replan loop. The Planner studies the board and forms a strategy. The Executor moves a piece. The Replanner looks at the new board and decides: "Is my strategy still good? Should I pivot? Or have I already won?"

🧠

⚡

🔍
Evaluate Replanner decides
Then the Replanner says: keep going, change course, or wrap it up →

The Shared Notebook

Before the three characters can work together, they need a shared notebook — something they all read from and write to. In the code, this notebook is a TypedDict called PlanExecuteState. Every node in the StateGraph reads from this notebook and writes back to it.

CODE 

class PlanExecuteState(TypedDict):
    """Plan-Execute-Replan 状态"""
    
    # 用户输入（任务描述）
    input: str
    
    # 执行计划（步骤列表）
    plan: List[str]
    
    # 已执行的步骤历史
    # 使用 operator.add 实现追加式更新（而非覆盖）
    past_steps: Annotated[List[tuple], operator.add]
    
    # 最终响应/报告
    response: str
PLAIN ENGLISH

Define the shared notebook as a typed dictionary — every field has a specific type.

(Docstring: this is the Plan-Execute-Replan state.)

(Comment: the user's question or task description.)

input: The user's question, stored as text. This never changes during the loop.

(Comment: the execution plan — a list of steps.)

plan: A to-do list. Steps are strings like "Check CPU metrics". The Executor reads from this list.

(Comment: history of completed steps.)

(Comment: uses operator.add to append instead of overwrite.)

past_steps: A running log of every step that was completed and what was found. New results are appended, never lost.

(Comment: the final answer.)

response: When this field gets filled in, the loop knows the job is done.

The state is the beating heart of the loop. The Planner writes a plan. The Executor reads the first step and appends results to past_steps. The Replanner reads everything and decides what comes next. When response is written, the music stops.

Wiring Up the Dance Floor

The state is the notebook. Now we need to wire up the dance floor — connecting our three nodes with edges so data flows through them in the right order. This is where StateGraph shines.

CODE 

    def _build_graph(self):
        """构建 Plan-Execute-Replan 工作流"""
        logger.info("构建工作流图...")

        # 创建状态图
        workflow = StateGraph(PlanExecuteState)

        # 添加节点
        workflow.add_node(NODE_PLANNER, planner)      # 制定计划
        workflow.add_node(NODE_EXECUTOR, executor)  # 执行步骤
        workflow.add_node(NODE_REPLANNER, replanner)  # 重新规划

        # 设置入口点
        workflow.set_entry_point(NODE_PLANNER)

        # 定义边
        workflow.add_edge(NODE_PLANNER, NODE_EXECUTOR)     # planner -> executor
        workflow.add_edge(NODE_EXECUTOR, NODE_REPLANNER)   # executor -> replanner

        # replanner 的条件边
        def should_continue(state: PlanExecuteState) -> str:
            """判断是否继续执行"""
            # 如果已经生成了最终响应，结束
            if state.get("response"):
                logger.info("已生成最终响应，结束流程")
                return END

            # 如果还有计划步骤，继续执行
            plan = state.get("plan", [])
            if plan:
                logger.info(f"继续执行，剩余 {len(plan)} 个步骤")
                return NODE_EXECUTOR

            # 计划为空但没有响应，返回 replanner 生成响应
            logger.info("计划执行完毕，生成最终响应")
            return END

        workflow.add_conditional_edges(
            NODE_REPLANNER,
            should_continue,
            {
                NODE_EXECUTOR: NODE_EXECUTOR,
                END: END
            }
        )

        # 编译工作流
        compiled_graph = workflow.compile(checkpointer=self.checkpointer)

        logger.info("工作流图构建完成")
        return compiled_graph

The conditional edge from Replanner is the magic. It turns a straight line into a loop: the Replanner either sends work back to the Executor (keep going) or hits END (we are done). The checkpointer saves the state at every step, so if the server crashes mid-investigation, the system picks up exactly where it left off.

The Safety Nets

Invisible guardrails that keep AI from spiraling into chaos

The Four Safety Nets

Think of these like training wheels that auto-deploy when you start wobbling. Most of the time you don't see them — but they're always there, ready to catch you before you fall.

Prototype AI is easy. production AI needs guardrails. SuperBizAgent has four hard safety limits that force the AI to eventually give you an answer — even if it's not perfect.

🛑

MAX_STEPS Limit

Forces a final answer after 8 total steps. No matter what the agent wants to do next — it's done. The ultimate last resort.

🚫

Replan Ban After 5

After 5 executed steps, the agent cannot choose "replan." It must either continue or respond. Prevents endless strategy pivots.

📏

Step Count Shrink

When the agent replans, the new plan can't have more steps than the old one had remaining. Prevents the agent from stalling forever.

✂️

Message Trimming

Limits conversation history to the system prompt + recent messages. Prevents the AI's memory from overflowing and crashing the session.

The Hard Stop: MAX_STEPS

The most important safety net is also the simplest: a hard cap on how many steps the agent can take. Without this, an agent that keeps choosing "replan" would run infinite loops, burning through your API budget.

Keeping the Desk Clean

Every message the AI sees takes up space in its context window. After a long conversation, that window overflows and the AI forgets what's happening. This middleware keeps the AI's desk clean by trimming old messages while preserving the system prompt.

CODE 

def trim_messages_middleware(state: AgentState) -> dict[str, Any] | None:
    messages = state["messages"]
    # 如果消息数量较少，无需修剪
    if len(messages) <= 7:
        return None
    # 提取第一条系统消息
    first_msg = messages[0]
    # 保留最近的 6 条消息
    recent_messages = messages[-6:] if len(messages) % 2 == 0 else messages[-7:]
    # 构建新的消息列表
    new_messages = [first_msg] + list(recent_messages)

The Traffic Controller

The should_continue function is a tiny piece of code with enormous power. It sits between the Replanner and the rest of the graph, reading the dictionary-based state and deciding: keep going, or stop?

This is the most common place for bugs to hide — not because the code is wrong, but because the AI's decision at this junction depends on what's in the state. Look at what actually happens:

CODE 

        # replanner 的条件边
        def should_continue(state: PlanExecuteState) -> str:
            """判断是否继续执行"""
            # 如果已经生成了最终响应，结束
            if state.get("response"):
                logger.info("已生成最终响应，结束流程")
                return END

            # 如果还有计划步骤，继续执行
            plan = state.get("plan", [])
            if plan:
                logger.info(f"继续执行，剩余 {len(plan)} 个步骤")
                return NODE_EXECUTOR

            # 计划为空但没有响应，返回 replanner 生成响应
            logger.info("计划执行完毕，生成最终响应")
            return END

        workflow.add_conditional_edges(
            NODE_REPLANNER,
            should_continue,
            {
                NODE_EXECUTOR: NODE_EXECUTOR,
