The Plan-Execute-Replan Loop

Think, act, evaluate, repeat — the three-step dance that turns questions into answers

Playing Chess With Yourself

Imagine a chess player studying the board and planning three moves ahead. But unlike real chess, after each move you get to look at the new board and change your strategy.

That is the Plan-Execute-Replan loop. The Planner studies the board and forms a strategy. The Executor moves a piece. The Replanner looks at the new board and decides: "Is my strategy still good? Should I pivot? Or have I already won?"

🧠
Think Planner strategizes
→
⚡
Act Executor takes action
→
🔍
Evaluate Replanner decides
Then the Replanner says: keep going, change course, or wrap it up →

The Shared Notebook

Before the three characters can work together, they need a shared notebook — something they all read from and write to. In the code, this notebook is a TypedDict called PlanExecuteState. Every node in the StateGraph reads from this notebook and writes back to it.

CODE 

class PlanExecuteState(TypedDict):
    """Plan-Execute-Replan 状态"""
    
    # 用户输入（任务描述）
    input: str
    
    # 执行计划（步骤列表）
    plan: List[str]
    
    # 已执行的步骤历史
    # 使用 operator.add 实现追加式更新（而非覆盖）
    past_steps: Annotated[List[tuple], operator.add]
    
    # 最终响应/报告
    response: str
PLAIN ENGLISH

Define the shared notebook as a typed dictionary — every field has a specific type.

(Docstring: this is the Plan-Execute-Replan state.)

(Comment: the user's question or task description.)

input: The user's question, stored as text. This never changes during the loop.

(Comment: the execution plan — a list of steps.)

plan: A to-do list. Steps are strings like "Check CPU metrics". The Executor reads from this list.

(Comment: history of completed steps.)

(Comment: uses operator.add to append instead of overwrite.)

past_steps: A running log of every step that was completed and what was found. New results are appended, never lost.

(Comment: the final answer.)

response: When this field gets filled in, the loop knows the job is done.

The state is the beating heart of the loop. The Planner writes a plan. The Executor reads the first step and appends results to past_steps. The Replanner reads everything and decides what comes next. When response is written, the music stops.

Wiring Up the Dance Floor

The state is the notebook. Now we need to wire up the dance floor — connecting our three nodes with edges so data flows through them in the right order. This is where StateGraph shines.

CODE 

    def _build_graph(self):
        """构建 Plan-Execute-Replan 工作流"""
        logger.info("构建工作流图...")

        # 创建状态图
        workflow = StateGraph(PlanExecuteState)

        # 添加节点
        workflow.add_node(NODE_PLANNER, planner)      # 制定计划
        workflow.add_node(NODE_EXECUTOR, executor)  # 执行步骤
        workflow.add_node(NODE_REPLANNER, replanner)  # 重新规划

        # 设置入口点
        workflow.set_entry_point(NODE_PLANNER)

        # 定义边
        workflow.add_edge(NODE_PLANNER, NODE_EXECUTOR)     # planner -> executor
        workflow.add_edge(NODE_EXECUTOR, NODE_REPLANNER)   # executor -> replanner

        # replanner 的条件边
        def should_continue(state: PlanExecuteState) -> str:
            """判断是否继续执行"""
            # 如果已经生成了最终响应，结束
            if state.get("response"):
                logger.info("已生成最终响应，结束流程")
                return END

            # 如果还有计划步骤，继续执行
            plan = state.get("plan", [])
            if plan:
                logger.info(f"继续执行，剩余 {len(plan)} 个步骤")
                return NODE_EXECUTOR

            # 计划为空但没有响应，返回 replanner 生成响应
            logger.info("计划执行完毕，生成最终响应")
            return END

        workflow.add_conditional_edges(
            NODE_REPLANNER,
            should_continue,
            {
                NODE_EXECUTOR: NODE_EXECUTOR,
                END: END
            }
        )

        # 编译工作流
        compiled_graph = workflow.compile(checkpointer=self.checkpointer)

        logger.info("工作流图构建完成")
        return compiled_graph

This is a conditional edge. It wires the Replanner to the decision function and specifies the possible routes.

The conditional edge from Replanner is the magic. It turns a straight line into a loop: the Replanner either sends work back to the Executor (keep going) or hits END (we are done). The checkpointer saves the state at every step, so if the server crashes mid-investigation, the system picks up exactly where it left off.

Why This Pattern Matters

💡
Aha! — The Adaptive Superpower

This pattern — Plan-Execute-Replan — is one of the most important AI agent architectures in use today. It separates "chatbots that answer questions" from "agents that solve problems." Most AI systems follow a rigid plan. This one adapts — it can abandon bad steps mid-investigation and try something else. That is what makes it feel almost human.

Scenario 2
