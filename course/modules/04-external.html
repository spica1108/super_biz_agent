The Outside World

APIs, databases, and why every external service is a ticking time bomb

A Journalist Writing a Story

Imagine a journalist reporting a breaking news story. They do not know everything by heart — they call sources on the phone (which might not pick up), dig through newspaper archives (which could be incomplete), and consult expert analysts (who might be busy or wrong).

That is exactly what this app does. It does not think in a vacuum — it reaches out to three external services for help. And just like the journalist, every source can be unreliable.

📞
Calling Sources — APIs

The app calls the LLM API for AI reasoning — like phoning an expert analyst. If the line is busy or the expert is rate-limited, the app has to cope.

📚
Checking Archives — Vector Database

The app searches a vector database for relevant context — like checking newspaper archives. If the archive is closed, the app answers from general knowledge alone.

🔧
Consulting Experts — MCP Tools

The app uses MCP tools to classify incidents and query live monitoring data — like asking a specialist to run diagnostics. If the specialist is off duty, the app detects it and keeps going.

Each external service is a ticking time bomb. Let us look at the three the app relies on.

Graceful Degradation in Action

When the app starts up, it tries to connect to Milvus. But what if Milvus is not running? Instead of crashing and burning, the app has a safety net. This is called graceful degradation: the core still works, just without vector search.

CODE 

# 连接 Milvus
logger.info("🔌 正在连接 Milvus...")
try:
    milvus_manager.connect()
    logger.info("✅ Milvus 连接成功")
except Exception as e:
    if not config.allow_missing_external_services:
        raise
    logger.warning(f"Milvus 暂不可用，开发降级模式继续启动: {e}")
PLAIN ENGLISH

(Comment: heading for this block of code — connecting to Milvus.)

Log that we are about to try connecting to the vector database.

try: Attempt this next operation, and if anything goes wrong, catch the error.

Execute the actual database connection — reach out to Milvus at the configured host and port.

If the connection succeeds, log a green checkmark and keep going.

except Exception as e: If anything at all goes wrong, catch the error instead of crashing.

if not allow_missing_external_services: raise — In production mode, crash because Milvus is required. In development mode, skip this.

This line runs if we are in development mode. Log a warning and keep the app running — this is graceful degradation.

The flag allow_missing_external_services is the key. In development, it lets the app start even when Milvus is down — you can test everything except vector search. In production, the app fails fast because there is no point running without a database.

The Configuration Dashboard

Every external service needs configuration: an address to reach it, a port to connect to, and sometimes a secret key. Here are the settings that tell the app where to find each service:

milvus_host The server address where Milvus is running — localhost means it is on the same machine
milvus_port The network port Milvus listens on — 19530 is the standard port
milvus_timeout How long to wait for Milvus before giving up — 10000ms (10 seconds)
dashscope_api_key The API key that authenticates your app to DashScope — loaded from the .env file
dashscope_model Which AI model to use for reasoning — qwen-max is the most capable
mcp_cls_url The web address of the Classification MCP server — http://localhost:8003/mcp
mcp_monitor_url The web address of the Monitor MCP server — http://localhost:8004/mcp
mcp_cls_transport Transport protocol for MCP communication — streamable-http

The External Dependency Rule

Every external service WILL fail at some point. The question is not "will it fail?" but "what does our app do when it fails?" Graceful degradation, retries, timeouts, and exponential backoff are what separate production apps from hobby projects.
