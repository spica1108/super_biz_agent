Meet Your Team

Think of SuperBizAgent like a hospital ER team. Every member has one job — and they hand off through clean interfaces. The complexity isn't in any single piece; it's in how they coordinate.

When you tell an AI coding tool "add a new feature," you need to know which component to put it in. That's what this module is for.

Key Insight

Splitting responsibilities into focused roles — engineers call it "separation of concerns" — is one of the most important ideas in software. Each piece is simple alone; the magic is in how they coordinate.

Where Everything Lives

In a well-organized project, the directory tells you what something does before you even open the file. Here's the map.

super_biz_agent/ Project root — everything starts here
app/ Main application code
api/ URL endpoints — the front door for every incoming request
services/ Business logic — where the actual diagnosis happens
agent/ AI brain — the Planner, Executor, and Replanner live here
tools/ Local helpers — built-in functions the agent can call directly
mcp_servers/ External tool servers — specialized connections to outside systems

Quick rule of thumb: Routes go in api/, logic goes in services/, data fetching goes in tools/, and complex external integrations go in mcp_servers/.

How Routes Get Registered

This snippet from app/main.py shows how each URL path is connected to its handler — like wiring a switchboard. Every framework has a moment like this where you plug everything together.

CODE 

# 创建 FastAPI 应用
app = FastAPI(
    title=config.app_name,
    version=config.app_version,
    description="基于 LangChain 的智能oncall运维系统",
    lifespan=lifespan
)

# 配置 CORS,允许任意来源访问 API
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],  # 生产环境应该限制具体域名
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

# 注册路由
app.include_router(health.router, tags=["健康检查"])
app.include_router(chat.router, prefix="/api", tags=["对话"])
app.include_router(file.router, prefix="/api", tags=["文件管理"])
app.include_router(aiops.router, prefix="/api", tags=["AIOps智能运维"])
app.include_router(embedding.router, prefix="/api", tags=["Embedding"])
PLAIN ENGLISH

Create the FastAPI app — the engine that powers the entire API. This is the central object everything plugs into.

Set the app name, version, and description (shows up in auto-generated docs for other developers).

Tie in startup/shutdown logic — like turning on the lights when the server starts and locking up when it shuts down.

Add CORS middleware — for development, allow any origin. The comment warns: restrict specific domains in production.

Allow credentials, any HTTP method, and any header. Development-friendly defaults.

Register the health check route (no /api prefix — monitoring tools need direct access).

Register feature routes under /api — chat, file management, AIOps, and embedding search. Each route group is a separate department with its own router file.

Good to Know

This file is the "switchboard" of the entire backend. If you ever wonder "where does this URL connect to?" — app/main.py is your first stop. The vector store connection and embedding setup also happen here.

Test Your Understanding

Three scenario questions. No trick answers — just applying what you just learned about who does what.

Scenario

Your monitoring system shows disk usage at 97%. You want to add a new component that checks disk space as part of the diagnosis flow. Where should you create it?

Why this matters: Local tools (in app/tools/) are the simplest way to add data-fetching capabilities. They're Python functions the agent can call directly. MCP servers (in mcp_servers/) are for tools that need special infrastructure — SSH access, authentication, or running as separate processes. For a simple server-local disk check, a tool is the right call. But if you needed to check disks across 50 servers with different credentials, an MCP server would be the better choice.

Scenario

Users report that the AIOps diagnosis takes too long — sometimes it times out entirely. Which component would you investigate first?

Why this matters: When diagnosing a timeout, follow the architecture. A slow individual tool (option d) can cause timeouts, but the service is where you'd notice the timeout happening — it's the component waiting for responses. The Router (option b) forwards requests almost instantly; it's never the bottleneck. This is a real debugging skill: knowing which layer to check first saves hours.

Scenario

Your team wants to add a "recent incidents" dashboard that shows the last 10 AIOps diagnoses. What backend components need to change?

Why this matters: Every feature touches specific layers. A simple data-query feature like "show recent items" uses the API layer (to define the URL endpoint) and the service layer (to query the data). The Agent is for real-time diagnosis orchestration, not for querying historical data. Knowing which layer to touch is exactly the kind of decision you'll make every day working with this system.
