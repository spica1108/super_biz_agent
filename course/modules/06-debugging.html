When Things Go Wrong

Real debugging scenarios — and how to think like a detective

The Flight Data Recorder

When a plane has an incident, investigators don't guess — they pull the flight data recorder (the black box) and replay every sensor reading and system state leading up to the moment. Debugging an AI agent works exactly the same way.

The bug isn't a typo — it's usually a decision the AI made that was reasonable in isolation but wrong in context. You debug by tracing the state through the LangGraph, not by reading code line by line. Every node leaves a trail — you just need to know where to look.

The Traffic Controller

The should_continue function is a tiny piece of code with enormous power. It sits between the Replanner and the rest of the graph, reading the dictionary-based state and deciding: keep going, or stop?

This is the most common place for bugs to hide — not because the code is wrong, but because the AI's decision at this junction depends on what's in the state. Look at what actually happens:

CODE 

        # replanner 的条件边
        def should_continue(state: PlanExecuteState) -> str:
            """判断是否继续执行"""
            # 如果已经生成了最终响应，结束
            if state.get("response"):
                logger.info("已生成最终响应，结束流程")
                return END

            # 如果还有计划步骤，继续执行
            plan = state.get("plan", [])
            if plan:
                logger.info(f"继续执行，剩余 {len(plan)} 个步骤")
                return NODE_EXECUTOR

            # 计划为空但没有响应，返回 replanner 生成响应
            logger.info("计划执行完毕，生成最终响应")
            return END

        workflow.add_conditional_edges(
            NODE_REPLANNER,
            should_continue,
            {
                NODE_EXECUTOR: NODE_EXECUTOR,
                END: END
            }
        )
PLAIN ENGLISH

(Comment: the Replanner's conditional edge — the decision point.)

Define a function called should_continue that reads the current state and decides where to go next.

(Docstring: "Determine whether to continue.")

(Comment: if a response already exists, stop.)

Check if the response field is filled — if yes, someone already wrote the answer.

Log: "Final response generated, ending flow."

Return END — the workflow is done. This is the exit door.

(Comment: if there are still plan steps, continue.)

Read the plan field. If there are steps remaining...

Log how many steps are left.

Return NODE_EXECUTOR — send the work back to the Executor for another round.

(Comment: no plan remaining, generate the response.)

Log that the plan is exhausted and a response is needed.

Return END — the Replanner will generate the final answer.

Wire up this decision function as a conditional edge from the Replanner node.

After the Replanner finishes, call should_continue.

If the result is NODE_EXECUTOR, loop back.

If the result is END, stop here.

See the pattern? The function checks two things: response (is there an answer?) and plan (is there more work?). If the Replanner never writes response and keeps adding to plan, this conditional edge sends the route back to Executor forever. That's where bugs come alive.

The Debugging Files

Three real incidents. For each one, the symptoms are described below — your job is to identify what went wrong and which component is responsible. Think like a detective, not a mechanic.

Case File #1

Your system is investigating a server CPU spike. After 45 minutes and 34 completed steps, the user is still waiting. The logs show the Replanner repeatedly saying "继续执行" and the plan keeps growing. No response has ever been written to the state.

Case File #2

A junior engineer runs a diagnosis for a database slowdown. The system completes in just 3 steps and produces a report that only mentions "check slow query logs" — completely missing the root cause. The engineer expected the system to check memory, disk I/O, and connection pools before drawing a conclusion. The state shows past_steps only has 2 entries.

When Bad Data Propagates

Some bugs are silent — they don't crash the system, they just corrupt the result. The most dangerous bugs are the ones that look like everything is working. Here's the trickiest scenario of the three.

Case File #3

The Executor fails on step 1 — "Check CPU metrics" — because the monitoring API returns an exception. But instead of stopping, the system continues to step 2 "Check error logs" and produces a report based on incomplete data. The logs show the error clearly, but the system never alerts anyone.

Cold Case

The diagnosis report contains correct data — all the numbers are accurate — but the formatting is broken: the text is garbled, sections are missing, and conclusions are hard to read. The data pipeline worked perfectly; something went wrong at the very end.

Cold Case

The app returns an empty response — no error, no crash, just blank. The user sees nothing. The logs show the workflow ran to completion but the final output was None.

The Secret Weapon

💡
The State Is Your Black Box

The most powerful debugging tool in LangGraph is the state. At any point, you can inspect plan, past_steps, and response to understand exactly what the agent is thinking. Most bugs become obvious the moment you look at the state at the moment of failure — the data tells you everything: what the agent knew, what it decided, and why.
